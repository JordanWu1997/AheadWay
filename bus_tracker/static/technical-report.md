# 1. 系統目標與閱讀方式

本系統讓乘客選擇路線、方向和站牌，同時查看**官方下一班預估**及**目前可辨識的後續公車**。例如，加入「橘5」並選「往捷運景安站／捷運景安站(景平路)」，畫面上方顯示官方預估，下方逐車列出沿線接近的車、下一站及推估到站範圍。官方資料沒有提供每輛後續車的獨立 ETA，因此逐車時間由本系統推估，兩種數字分開標示。初次開啟顯示簡短使用指引與空白路線清單；乘客可搜尋臺北／新北路線名稱，或貼上官方 `route.jsp?rid=...` 連結加入分頁。例如 `rid=10841` 可加入 0東，站牌與動態改由臺北市資料提供；分頁偏好只存於該瀏覽器。

這份報告描述目前程式的實際行為。介面上的「即時」表示定期取得上游資料，並非車輛每秒傳送位置。例如乘客在 07:30 開啟頁面，可能看到 07:29:40 的車輛回報；頁面會顯示資料時間，而不會把它說成 07:30 的精確位置。

# 2. 系統全貌與技術堆疊

```
乘客瀏覽器（HTML + CSS + 原生 JavaScript）
    │  GET 路線、站牌、到站快照；POST 語音／通知
    ▼
Python 標準函式庫 HTTP 伺服器（server.py）
    ├── feeds.py + catalog.py：臺北／新北資料來源、路線搜尋與連結驗證
    ├── FeedCache + tracker.py：官方 gzip/JSON 資料、逐車位置與 ETA
    ├── calibration.py：SQLite 到站誤差樣本
    ├── speech_audio.py：eSpeak NG 或本機 OpenAI 相容 TTS → WAV
    ├── push.py：Web Push 訂閱、VAPID 與送訊
    └── schedule.py + scheduled_voice.py：擁有者的 cron 定時語音
```

前端沒有 React 或打包流程：`static/index.html` 提供結構，`static/style.css` 負責外觀與響應式配置，`static/app.js` 負責資料請求、狀態、互動、地圖及語音。例如切換「921」分頁時，JavaScript 改變目前路線、載入 921 站牌，並用該路線的狀態重新畫到站卡與路線圖。加入新路線時，前端透過 `/api/catalog` 搜尋、取得方向與來源資訊，再將路線 ID 存在瀏覽器；公開訪客不會因此改動其他人的分頁。

後端使用 Python 的 `ThreadingHTTPServer`，並非 Flask 或資料庫驅動的全站框架。它將資料整理成 JSON 給瀏覽器，亦提供靜態頁面、語音 WAV 及技術報告。例如 `GET /api/arrivals?route_id=16405&direction=0&stop_id=...` 會回傳所選站牌的官方狀態、逐車清單、路線狀態與資料擷取時間；`POST /api/voice` 回傳 `audio/wav`。

| 元件 | 目前用途 | 具體例子 |
|---|---|---|
| HTML / CSS / 原生 JS | 頁面與互動 | 站牌下拉選單、可新增的路線分頁、語音設定 |
| Python 標準函式庫 | HTTP API、抓取及計算 | `server.py`、`tracker.py` |
| 官方臺北／新北市公車 feed | 路線、站序、車輛、事件、官方 ETA | 各來源的 `GetBusData.gz` 提供車輛座標 |
| SQLite | 校正預測誤差、儲存推播訂閱 | 使用過的路線各有到站歷史檔 |
| eSpeak NG / 本機 TTS | 伺服器端合成語音 | 朗讀「下一班約 5 分鐘」並傳 WAV 給手機 |
| Browser Speech API | 裝置自己的語音 | 選手機已安裝的中文聲音朗讀 |
| cron / PulseAudio | 擁有者每天定時朗讀 | 每天 07:30 開始，每 5 分鐘播報 |
| Tailscale Funnel | 對外 HTTPS | `https://pop-os.tail443eb6.ts.net/bus/` |

## 如何新增路線，以及資料儲存在哪裡

初次使用時，乘客按「加入第一條路線」開啟搜尋；已有路線時，按分頁右側的「＋ 加入路線」。可搜尋路線名稱，或從[官方路線清單](https://pda5284.gov.taipei/MQS/routelist.jsp)複製路線連結貼上。例如貼上 `https://pda5284.gov.taipei/MQS/route.jsp?rid=10841`，瀏覽器向 `/api/catalog?q=...` 查詢。後端只接受該官方網域與 `/MQS/route.jsp` 路徑，取出數字 `rid=10841`，再從臺北、新北兩個官方 Route feed 找到 0東、方向與資料來源。搜尋「0東」則以官方 feed 內的名稱查找，最多回傳 25 筆。貼入的網頁本身不被下載來計算到站；若路線不在這兩個 feed 中，頁面會顯示目前無法追蹤。移除分頁時須確認，且會一併刪除該路線在此瀏覽器的常用行程；若有綁定手機通知或定時語音排程，須先關閉提醒。

乘客點選結果後，瀏覽器把路線 ID 加入分頁並請求 `/api/stops?route_id=10841` 與 `/api/arrivals?...`；後端依路線資料來源選臺北或新北的 Stop、BusData、BusEvent、EstimateTime feed，交給同一套到站計算。重新開啟頁面時，瀏覽器用 `/api/routes?ids=...` 重新取得名稱與方向。路線清單由乘客自行建立，最多可加入 20 條；分頁旁的垃圾桶按鈕會顯示目前路線名稱並開啟確認。移除會刪除該路線在此瀏覽器的常用行程。

| 位置 | 保存內容與期限 | 0東的例子 |
|---|---|---|
| 此網站的瀏覽器 `localStorage` | 新增路線 ID `bus-tracker-added-routes`、目前路線 `bus-tracker-route`、每條路線的方向／站牌／跨方向選擇、最多八筆常用行程。持續到使用者清除該網站資料。 | 只保存數字 `10841` 與站牌選擇；不保存完整官方站牌與車輛表。 |
| 每個伺服器程序的記憶體 | 約每小時檢查官方 Route feed 是否有新 ID；已載入路線的名稱與方向保留到伺服器重啟。Route／Stop feed 約快取一小時，車輛／事件／ETA 約快取 30 秒；近期站間實測存在記憶體。 | 網頁重開後由伺服器再次提供 0東名稱、方向與站牌，不靠瀏覽器內的舊資料。 |
| 伺服器 SQLite | 第一次追蹤某路線時建立該路線的到站預測與誤差檔；啟用手機推播才儲存訂閱與選定路線、站牌。資料不因關閉分頁而刪除。 | 0東會使用 `arrival_history_10841.sqlite3`；手機通知另存於 `push_subscriptions.sqlite3`。 |
| 擁有者的排程檔 | 只有擁有者儲存每日語音排程時才更新 `schedule.json`；公開訪客無編輯權限。 | 設定「每天 07:30 朗讀 0東某站」才會把路線 ID 與站牌寫入排程。 |

瀏覽器資料以**來源網址**區分。例如同一人在手機 `https://pop-os.tail443eb6.ts.net/bus/` 新增 0東，電腦或 `http://127.0.0.1:8000/` 不會自動出現該分頁。清除手機瀏覽器的網站資料會移除其分頁與常用行程，但不會刪掉伺服器的 ETA 校正紀錄；其他乘客也不會看到這部手機新增的分頁。公開版與擁有者版是不同程序，各自維持記憶體快取，但使用同一組官方資料端點。

# 3. UI／UX 與手機、電腦的 RWD

頁面依乘客決策順序排列：**路線分頁 → 行程與站牌 → 到站資訊 → 已辨識的後續公車 → 出發建議 → 沿線路線 → 語音提醒**。官方下一班與逐車推估各有明確標籤；資料時間、推估範圍及「下一輪須折返續行」的條件也直接顯示。改選路線或站牌時，舊站結果先清空，再讀取最近資料與最新資料，避免把前一站的車誤當新站來車。

六張主要卡片（行程與站牌、到站資訊、沿線公車、出發建議、路線檢視、語音提醒）都可收合。標頭採同一規則：**左側是英文眉標與中文主標，右側是當前路線／站牌、查詢時間、車輛數、簡短出發建議或語音狀態，最右為同尺寸的方形箭頭**。展開時箭頭向上，收合時向下；標頭整列可點，路線檢視的獨立按鈕保留至少 44px 的操作高度。卡片間距統一 16px，收合後仍能讀到決策所需的簡短資訊。例如「建議出發時間」收合時顯示「09:04 前出發」，展開後才呈現條件、步行時間與完整說明；語音設定的摘要會隨模式、播報間隔／門檻、語言、詳細程度與語音來源同步更新。

路線分頁右側使用具名的「＋ 加入路線」按鈕，開啟後變為「× 關閉」。搜尋區先提供路線名稱或官方連結輸入框與搜尋結果，較長的新增說明收在「如何新增路線？」。只有分頁實際超出可用寬度時才顯示左右箭頭；箭頭佔自己的位置，不覆蓋分頁。路線列表可搜尋站名、跳至所選站牌，逐站顯示官方狀態與近期車輛事件。路線圖以藍色箭頭標記選站，去程／返程線與公車數標記各用其方向色；可拖曳與縮放，但站點連線僅是位置示意，不是道路導航圖。

畫面以 **650px** 為主要斷點。桌面版內容寬約 1020px，兩方向站牌並排，路線圖直接展開，語音選項以兩欄排列。手機版先顯示站牌清單，路線圖和語音詳細設定可另外展開；常用行程收合時最多顯示五筆，更多項目可展開。「手機出發提醒」在出發卡內另有摘要與收合控制。390px 手機上標頭右側資訊會適度換行；320px 寬仍不產生水平溢出。選站欄滑出畫面後，可用頂端追蹤摘要返回所選站牌。

品牌只稱 **AheadWay**。頁首將 Ahead 設為深綠、Way 設為珊瑚橘，標誌 `static/LOGO.jpeg` 等比縮入方形。橫幅 `static/BANNER.jpeg` 位於語音卡之後，手機與桌面按原比例顯示，並可點擊檢視完整圖。兩張圖片各附內容版本參數，更新圖片後瀏覽器會取得新版。

# 4. 官方資料、逐車定位與到站計算

伺服器從臺北市 `blobbus` 或新北市 `ntpcbus` 公開 feed 讀取 gzip 壓縮 JSON：`Route`（路線及路徑 ID）、`Stop`（站牌及方向）、`BusData`（車輛 GPS）、`BusEvent`（進出站事件）、`EstimateTime`（官方站牌 ETA）。例如一筆 BusEvent 指出車牌 ABC-1234 剛離開中興街口，BusData 提供它的座標，EstimateTime 可能同時指出景安站下一班還有 4 分鐘。`feeds.py` 選來源，`catalog.py` 將搜尋詞或官方連結轉成路線 ID；伺服器僅查找固定的兩個資料來源，不依使用者貼上的任意網址抓資料。若官方清單上的路線不在這兩個來源，搜尋會顯示目前不支援。

逐車定位先檢查路線／路徑 ID、服務狀態、車牌與時間；超過 **4 分鐘**的車輛或事件會略過。GPS 點會投影到相鄰站牌座標所形成的折線，求出「第幾站到第幾站之間」的連續進度及偏離折線的距離；偏離超過 **400 公尺**時不用該 GPS。若進出站事件與 GPS 的進度衝突太大，優先使用有效的事件。例如 GPS 看似已過兩站，但最新事件說剛離開中興街口，系統會避免直接把車顯示在景安站之後。因路線圖是直線示意，彎路、重疊道路或定位誤差仍可能造成錯配。

每一段相鄰站牌的行車秒數，依序取：(1) 近 3 小時同車通過相鄰站的觀察中位數；(2) 兩站官方 ETA 的合理正差值；(3) 依站距估算的備用值。對長於 2 公里的區間，備用規則容許較長行車時間。例如 A→B 實測 90 秒、B→C 官方差值 120 秒，而一輛車在 A→B 中途約一半位置，目標是 C，基礎推估約 `0.5 × 90 + 120 = 165 秒`。它是**車輛估計**，不是官方逐車預測。

系統會儲存預測及實際到站樣本於各路線的 SQLite 檔，用近來誤差調整逐車到站範圍；樣本不足時使用較保守的預設範圍。高／中／低「信心」是依資料年齡、定位偏差、區間來源及校正樣本設計的經驗標籤，並非機率。例如同車 40 秒前回報、路段有實測資料，可信度可能高於一輛 3 分鐘前回報、兩段都只靠站距估算的車。區間觀察值存在伺服器記憶體，重啟會清空；SQLite 的預測誤差樣本會保留。

**納入另一方向後續車**可套用到任何選定站牌。開啟後，系統把另一方向車輛到該方向終點的剩餘時間、端點折返時間，以及下一輪所選方向從起點到所選站牌的時間相加；只對兩端座標相距 1 公里以內的路線作此推估。例如在橘5去程選「捷運景安站(景平路)」，返程車必須先到返程末端，再接續下一輪去程，才會被列成「下一輪推估」。此時車輛可能在終點停駛或休息，因此以低信心標示；若本方向沒有可趕上的車，出發卡可顯示明確附條件的下一輪參考時間，但手機推播與到站門檻提醒不採用它。橘5官方站序把景安站列在返程，但實際去程在中興街口之後也抵達此站；系統仍將該站接到去程末端。已轉為返程的車只有在新鮮事件確認仍停於共同站牌時才標示為「本站」。

官方狀態與逐車位置可能看似矛盾，原因是兩者由不同 feed 提供。例如景安站顯示「今日未營運」但路線上仍見到一輛車，表示該站官方 ETA 回傳營運狀態，同時另一筆車輛位置仍可見；無法僅憑車的位置保證它將提供該站的載客服務。介面將「官方下一班」與「已定位的接近公車」分開顯示，並顯示資料年齡。

# 5. 更新、快取與錯誤狀態

平時網頁每 **30 秒**輪詢一次。路線／站牌 feed 約快取 1 小時，車輛、事件、官方 ETA 約快取 30 秒。乘客主動換站或按「更新」時，畫面立即清除舊站資訊，同時取最近可用快照與要求較新 feed；伺服器仍設共用**最短 5 秒**擷取間隔，以免頻繁操作壓垮上游。例如連續三次快速切換站牌，頁面會立刻顯示新選擇，並可能先拿到最近快取，稍後再拿到新資料，而不承諾每次按鍵都會讓官方 feed 更新。

前端用 `AbortController` 取消過時請求，並以遞增版本號避免舊回應覆蓋新站牌。例如先選 A 再立刻選 B，就算 A 的請求最後才回來，也不能把 A 的公車放到 B 卡片。新資料失敗時，若有最近可用資料，介面會明示目前顯示最近資料；無資料時顯示錯誤。語音與出發建議也根據目前的快照更新。

# 6. GPS 步行時間與出發建議

乘客可手動輸入「步行到站」分鐘數，也可開啟「使用目前位置」開關。預設為手動，分鐘欄顯示「手動設定」；開啟後，瀏覽器要求**一次**定位，欄位暫時唯讀並顯示「定位中 · 暫用手動」，成功時改顯示「依目前位置」、取得位置的時間及推估分鐘數。手機計畫模式使用同一卡片的「使用目前位置」開關，因此不會出現第二份定位欄位或出發建議。此時可按「重新定位」再量一次；換站且開關仍開啟時也會重新定位。例如 07:30 得到步行 8 分鐘，走了一段路後於 07:33 按「重新定位」，可能變為 5 分鐘，手機提醒門檻也隨之同步。分鐘欄維持唯讀，背景色區分 GPS 與手動狀態；關閉開關就恢復先前儲存的手動值。若權限遭拒、定位逾時、站牌缺座標或瀏覽器無定位能力，開關自動回到關閉狀態，顯示原因並恢復手動分鐘數。計畫模式的定位只在當次網頁工作階段有效，重新開頁預設手動；手動分鐘數則儲存在該瀏覽器。

計算會將乘客座標與所選站牌座標用球面距離公式估算直線距離，再用 **1.35 倍繞路係數、定位精度補償與 1.2 m/s 步速**換算時間。例如直線距離 400 公尺、定位精度補償 20 公尺，估算約 `ceil((400×1.35+20)/1.2/60)=8 分鐘`。它不是步行導航，也沒有使用街道、號誌或坡度。乘客座標只在瀏覽器計算，傳給伺服器的是結果分鐘數（例如推播設定的 `walk_minutes`），不是座標；舊定位回應也不能覆蓋已切換的新站或已關閉的開關。

出發建議將步行分鐘數再加固定 **2 分鐘**緩衝。若官方下一班的剩餘時間足夠，就根據官方 ETA 建議何時出發；否則依序尋找本方向、另一方向下一輪之中，推估區間下界仍足夠的車。後者明示「若此車在終點折返續行」，不能當成已確認班次。例如步行 5 分鐘、緩衝 2 分鐘、官方車 4 分鐘後到，系統不會建議追這班；如果本方向另一輛車的保守下界還有 12 分鐘，可能建議約 5 分鐘後出發。官方 ETA 依 feed 擷取時間遞減，車輛 ETA 依回報時間遞減；網頁每 10 秒重算建議及逐車時間，資料超過 4 分鐘則暫停建議。這是輔助決策，塞車、臨時改道與定位延遲仍會改變結果。

# 7. 電腦與手機的語音選擇

語音有**到站提醒**與**定時播報**兩種模式。到站提醒可選 1／3／5／10 分鐘或自訂 **1–60 分鐘整數**；官方 ETA 首次進入門檻時報出，也對進入門檻的本方向車輛避免重複地通知。例如自訂 12 分鐘，官方預估還有 11 分鐘時可觸發提醒；儲存擁有者排程時也會存入同一門檻。定時播報啟用後立即朗讀一次，之後依使用者設定的 **1–60 分鐘**間隔報出官方狀態與所有已辨識沿線車。例如設每 5 分鐘播報，07:30 開啟後會先聽到當下資訊，再於約 07:35 聽到新資訊。頁面上的手動語音需保持頁面開啟；「試播目前資訊」可直接檢查音效。

「播報內容」預設**簡短**：有可追蹤車輛時，只朗讀所選路線、方向、站牌，以及每輛公車的編號與推估到站時間；不重複朗讀官方下一班，也不唸車牌或下一站。沒有可追蹤車輛時，會改說官方狀態。選**詳細**則保留原本的官方資訊、車牌、站數與下一站。例如同時有兩輛返程公車可能在下一輪抵達時，先說一次「另一方向公車若在終點折返續行」，再依序報出兩輛車的時間，不重複警語。中文和 English、網站試播與定時排程都使用所選格式；既有未重新儲存的 cron 排程維持原本的詳細播報。

語言可選中文或 English，內容與對應聲音選項一起切換；網頁的主要視覺標籤仍是中文。聲音來源有三種：(1) 瀏覽器 `speechSynthesis` 列出的裝置聲音；(2) 伺服器的 eSpeak NG 中／英語各八種變體；(3) 本機 OpenAI 相容 TTS 伺服器。若瀏覽器聲音回報 `synthesis-failed`，頁面會要求後端 eSpeak 生成 WAV 作為備援。例如手機沒有可用的繁體中文瀏覽器聲音時，仍可選 eSpeak 中文；電腦使用者則可選本機 TTS 的 `tts-1 / anne`。實際可用聲音依裝置與本機 TTS 服務而定。

選本機 TTS 時，瀏覽器向同源 `/api/voice` 發送文字和 `model`、`voice`，**Python 伺服器**再向 `http://127.0.0.1:8001/v1/audio/speech` 發送 `{"model":"tts-1","input":"...","voice":"anne","response_format":"wav"}`，正規化 WAV 標頭後回傳瀏覽器。這樣外部手機不必連進伺服器的 8001 埠。例如手機打開公開網址後選「本機 TTS」，只連公開的 `/bus/api/voice`；是家中主機去呼叫自己的 8001。公開版預設 `tts-1 / anne`，為相容舊版也接受 `alloy`，以及列出的 eSpeak 聲音，擁有者本機版可在進階設定輸入本機 TTS 支援的模型與聲音名稱。

每天定時語音屬於**擁有者本機版**。儲存排程會把路線、站牌、模式、語言、聲音、開始時間和持續分鐘數寫入 `schedule.json`，並安裝一筆使用者 `cron` 工作；排程程序以鎖避免重疊。瀏覽器聲音在無瀏覽器的 cron 中不可用，會改用該語言的標準 eSpeak。例如每天 07:30 開始播報 60 分鐘、間隔 5 分鐘，即使關掉網頁，電腦保持開機、音效工作階段可用且上游可連線，仍可朗讀。公開版不提供排程編輯。

# 8. 手機背景通知與語音的界線

公開 HTTPS 頁面可註冊 Service Worker 與 Web Push 訂閱。伺服器保留裝置訂閱，約每 **30 秒**檢查新資料；當官方 ETA 或符合條件的本方向逐車推估落入「步行時間＋2 分鐘」出發視窗時，推播文字提醒。**跨方向下一輪車不觸發手機通知**。通知只採用三種資料來源皆在 90 秒內取得、車輛回報不超過 90 秒且信心不低的資料；判斷時扣除官方 feed 擷取後及車輛最後回報後已過的時間。例如步行 5 分鐘、緩衝 2 分鐘，官方 ETA 在 feed 擷取時為 8 分鐘、過了 1 分鐘才檢查，實際比較的是約 7 分鐘。若跳過理想出發窗口，通知文字會說「可能已來不及」，讓乘客自行確認。

手機訂閱有**固定提醒目標**。啟用通知時，網頁把當時路線、方向、站牌與步行分鐘數存於該瀏覽器，伺服器也保存相同目標；之後瀏覽其他路線不會改掉它。通知區明示「提醒目標」，瀏覽不同站牌時顯示「改為提醒目前站牌」，只有按此鈕才切換目標。例如固定橘5中興街口後查看 908，仍提醒橘5；按下切換鈕後才改提醒 908。停留在固定站牌時，手動步行分鐘數或定位估算變動仍會同步更新提醒門檻；查看其他站牌期間不改變已固定的步行分鐘數。同步時畫面顯示「正在同步」，失敗則顯示「重試同步」和可能仍在追蹤上次成功站牌的警語。每次更新附上該瀏覽器持續遞增的版本號；伺服器在 SQLite 記錄各訂閱的最新版本，拒絕後送達的舊選站更新或舊的啟用要求，並在回應標示是否套用。例如明確將提醒目標由 A 切至 B 時，即使 A 的儲存請求較晚到達，B 仍是提醒目標；關閉通知後，晚到的舊儲存請求也不能重新啟用。只改步行分鐘數時保留同輛車 15 分鐘內的去重紀錄，避免 GPS 重算造成重複通知；改站則重置該紀錄。訂閱按裝置分開，推播送達仍受手機系統與瀏覽器影響。

Web Push 在關閉頁面後可以顯示**文字通知**，但不能保證背景自動播音。iPhone／iPad 使用此功能前需先將公開頁面加入主畫面。例如手機鎖定時可看到出發通知；想聽到中文或英文語音，需開啟網頁並使用語音模式。推播使用 VAPID 私鑰與 SQLite 儲存訂閱；私鑰更換後裝置需重新訂閱。公開服務對訂閱總數及請求頻率設限。

手機提醒分成兩個工作模式。**計畫模式**用手動步行分鐘數或一次目前位置，直接使用合併後卡片上方的出發建議；切換站牌、修改步行時間、收到新到站資料以及每 10 秒的倒數更新，都會重新計算。背景 Web Push 位於兩種手機模式下方，可在任一模式中獨立啟用或關閉。例如 07:30 步行 5 分鐘、官方車 12 分鐘後到時，卡片可能建議約 5 分鐘後出發；07:33 收到 ETA 更新後會顯示新的時間。**前往站牌模式**則用 `watchPosition` 持續取得這部手機的位置，每次成功定位都重新估算到所選站牌的步行時間，並與新到站資料比較；換站時也會用最近的位置重算。若 ETA 扣掉步行估算及 2 分鐘緩衝後少於 2 分鐘，畫面提示「請加快腳步」；若 ETA 已短於步行估算，提示「這班可能趕不上」，並顯示頁底浮動警示。例如估算步行 5 分鐘、官方下一班還有 6 分鐘時，僅剩約 1 分鐘緩衝，因此提示加快；ETA 降到 4 分鐘時提示可能趕不上。這是按預設 1.2 m/s 推算的所需時間，**沒有量測使用者實際步速**，也沒有道路導航。

前往模式只在網頁開啟且手機允許定位時持續運作，離開此模式或頁面卸載會停止追蹤；回到暫停的頁面可重新開始定位。定位超過 90 秒、任何必要的公車資料超過 120 秒、位置精度差於 250 公尺或沒有可信本方向車輛時，會改顯示資料不足，不給確定的趕車判斷；低信心車及可能折返的下一輪車不作為趕車警告依據。官方 ETA 與逐車估算可能指向同一輛車，因此有官方下一班時以官方時間判斷；較晚逐車估算僅提示乘客確認是否真為另一班。例如官方 4 分鐘、另一筆車輛推估 5 分鐘時，不會直接宣稱 5 分鐘那筆是下一班。新警告可在頁面開啟時震動手機，已授權通知且 Service Worker 可用時亦嘗試顯示本機通知；裝置可能限制震動或通知。背景推播若先前已啟用，切到前往模式後仍會運作，但關頁後不能依手機移動位置即時調整步行分鐘數。

# 9. 對外 HTTPS、Tailscale Funnel 與安全邊界

此部署不需要家用路由器做 port forwarding，也不要求固定外網 IP 或自有網域。主機有兩個只綁在 `127.0.0.1` 的 Python 程序：擁有者版在 **8000**，公開受限版在 **8765**。Tailscale Funnel 在公網 **443/HTTPS** 接收連線，替 `*.ts.net` 網址處理憑證，再把 `/bus` 轉給 `http://127.0.0.1:8765`。例如外部手機開 `https://pop-os.tail443eb6.ts.net/bus/`，Funnel 轉到 8765，並非手機直接訪問區網的 8765。未來個人網站可用同一 443 和主機名稱的 `/` 路徑轉到另一個本機服務，例如 9000。

```
外部手機 ── HTTPS :443 ── Tailscale Funnel
                                  ├── /bus → 127.0.0.1:8765（公開公車頁）
                                  └── /    → 127.0.0.1:9000（未來個人網站）
本機擁有者瀏覽器 ── HTTP ───────→ 127.0.0.1:8000（可編輯 cron）
公開頁要求語音 ── /bus/api/voice → 8765 → 127.0.0.1:8001（TTS）
```

公開版只允許匿名訪客做必要的讀取，以及受限制的語音與推播訂閱 POST；排程 POST 被拒絕。公開語音檢查 HTTPS Origin、限制模型與聲音、文字長度、每 10 分鐘最多 **60 次**且最多 **2 個**同時合成；推播亦有頻率／容量限制。例如訪客不能透過公開網址改掉擁有者 07:30 的 cron 工作，也不能指定公開 TTS 使用任意模型。這些是資源與操作限制，並不是使用者登入系統；知道公開網址的人仍可瀏覽公車資料。

兩個程序可由 `deploy/bus-tracker-owner.service` 和 `deploy/bus-tracker-public.service` 啟動。公開版、Tailscale、網路、上游 feed 與所選 TTS 服務必須持續工作，對應功能才能運作。例如公開頁能載入但本機 8001 未運作時，官方到站資料仍可查看，選本機 TTS 播音則會失敗。

# 10. 限制、維護與延伸

到站推估受資料新鮮度、GPS 偏差、閉合路線、車輛折返及道路狀況影響。官方 feed 只提供站牌下一班預估，系統只能列出近期資料中可定位的後續車。例如一輛車未回報 GPS、亦沒有新鮮進出站事件，就不會被「所有接近公車」清單憑空補出來。地圖是停靠站座標示意，不應當作實際道路路徑；GPS 步行時間亦只是粗估。

未來可擴充真正的步行路網、個人實際步速估計與個人化出發緩衝；目前只有計畫模式的一次定位和前往模式的頁面內持續定位，都在瀏覽器換算分鐘數。例如若未來接入道路導航，就可把「直線 400 公尺推估 8 分鐘」改為「沿人行道 650 公尺約 9 分鐘」；這尚未實作。`voice_tools.py` 另提供可供 Hugging Face `speech-to-speech` 使用的唯讀查詢工具，但完整語音對話管線尚未在此專案安裝、執行或驗證。例如日後可問「908 到景安站還有幾班」，目前網站已提供播報，但不等於已有完整語音問答。

## 已完成的 UX 改進與後續注意事項

已把**正在查看**和**手機正在提醒**拆開：提醒目標會固定顯示，切換路線只改畫面，按「改為提醒目前站牌」才更新訂閱。目前若路線綁定了手機通知，移除確認會提示先關閉通知，避免失去管理提醒的分頁；定時語音排程亦同。切換路線仍不會更改已固定的通知目標。

## 介面語言與擴充

儀表板預設使用繁體中文；頁首「中／EN」兩個按鈕可直接切換語言。`aheadway-ui-language` 儲存在瀏覽器 `localStorage`，頁面重新載入後保留。介面語言只控制網站文案；「播報語言」仍由語音設定獨立控制，所以英文介面可以試播中文，預覽會顯示實際朗讀的句子。

`static/i18n.js` 是介面字表。`zh-TW` 使用 `index.html` 與 `app.js` 內的繁體中文來源文字，`en` 字表提供完整句子的 `exact` 對照、可重用片語的 `phrases` 對照，以及有數量或時間的動態格式。新語言可複製 `en` 字表、翻譯其值，再加入 `locales`；瀏覽器語言代碼放在 `htmlLang`。新增語言時，需在頁首切換組加入對應按鈕，並提供 `patterns` 與 `fallback` 以決定數量、時間和標點格式。修改來源中文後，需同步檢查字表；優先為完整句子加入對照，避免片語組合產生不自然語序。

路線與站牌專有名稱優先取路線目錄及 API 的 `nameEn`、`headsEn`、`nextStopEn`。資料沒有對應名稱時，保留來源名稱，避免錯誤音譯。到站、路線列表、離站建議、通知狀態等非同步更新由 DOM 觀察器套用字表。新增動態提示時，需在字表加入完整句子或數值樣板，並以中英切換、不同路線和手機寬度檢查。`/i18n.js` 同時經由公開 `/bus/` 路徑提供。
