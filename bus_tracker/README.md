# AheadWay

Author: Jordan · jordankhwu@gmail.com. The [technical report](static/technical-report.md) explains the interface colors and where to change them in `static/style.css` and `static/app.js`.

The header fits the complete `static/LOGO.jpeg` inside its mark and colors Ahead green and Way orange. The full `static/BANNER.jpeg` artwork is available below the rider controls and loads when scrolled into view. Both image URLs include a content version so browsers receive updated artwork despite the server's one-day cache. The header and footer link to Jordan's [GitHub](https://github.com/JordanWu1997) and email with recognizable icons. The restored title reads “下一班，還有下幾班。” in green and orange; the orange route badge aligns with the first route tab and is slightly larger. The arrival heading, data freshness, and official ETA share one card; the detected bus list remains a separate card. Jordan developed the site with design and implementation assistance from GPT-6-Sol in [Codex](https://openai.com/codex/).

Small local web app for a selected Taipei or New Taipei bus stop. 橘5, 908, and 921 are the initial tabs; use **加入其他路線** to search by route name or paste a link from the [official Taipei route list](https://pda5284.gov.taipei/MQS/routelist.jsp). For example, `https://pda5284.gov.taipei/MQS/route.jsp?rid=10841` adds 0東. Added tabs are stored in this browser and can be removed. Tabs switch the map, stops, official next arrival, following vehicles, and spoken reports. Each detected approaching vehicle has an estimated arrival time and next stop. Route and stop selections are saved per route in the browser. The optional **納入另一方向後續車** switch adds vehicles on the opposite leg if they finish that leg and continue into the next circuit to the selected stop. It starts off for newly added routes; enable it only when buses may continue into another trip. These next-circuit arrivals are uncertain: departure advice can show a conditional suggestion for them, while phone push and threshold alerts still exclude them.

## Public HTTPS with Tailscale Funnel

Funnel terminates HTTPS on public port 443 and proxies to a local HTTP port. The Python server does not need a certificate or port 443. Run the owner dashboard on localhost port 8000 and a separate read-only viewer on localhost port 8765:

```sh
cd /home/jordan/Desktop/Bus_Tracker
python -m bus_tracker.server 8000             # owner dashboard, localhost only
python -m bus_tracker.server 8765 --public --public-host=pop-os.tail443eb6.ts.net
```

The public viewer supports route data, live arrivals, browser speech, eSpeak, and the local OpenAI-compatible TTS server. It accepts only `/api/voice` and `/api/push-subscription` as public POST requests; schedule editing and the saved schedule remain private. Public requests require an HTTPS Origin matching `--public-host`. Public speech defaults to `tts-1` / `anne` (with `alloy` accepted for older clients) for the API engine or listed eSpeak voices, limits text to 1,000 characters, and caps shared traffic at 60 requests per 10 minutes with two concurrent syntheses. Phone notification subscriptions have a separate request rate limit and a 64-device capacity. Do not route Funnel to port 8000 or directly to the TTS server on port 8001. Change `--public-host` if the device's Tailscale hostname changes.

After enabling Funnel in the Tailscale admin console, publish **only** the viewer under `/bus`:

```sh
tailscale funnel --bg --https=443 --set-path=/bus http://127.0.0.1:8765
tailscale funnel status
```

Open the HTTPS URL shown by `tailscale funnel status` with `/bus/` appended. Test it from a device outside your LAN. Funnel supplies the HTTPS certificate for the `*.ts.net` hostname. A future personal website can run locally on another port (for example 9000) and use the same public HTTPS port and hostname at `/`:

```sh
tailscale funnel --bg --https=443 --set-path=/ http://127.0.0.1:9000
```

The `/bus` route remains the more specific path. Check `tailscale funnel status` after adding the root route. To remove only the bus route, use `tailscale funnel --https=443 --set-path=/bus off`. Anyone on the Internet can open a Funnel URL. Speech consumes resources on your computer; the global limits protect capacity but do not provide per-user identity. The host, Python viewer, TTS server, and Tailscale must remain running for API speech to work. For automatic startup on login, install the two example user services. Stop any manually running server on port 8000 before starting the owner service:

```sh
mkdir -p ~/.config/systemd/user
cp deploy/bus-tracker-owner.service deploy/bus-tracker-public.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now bus-tracker-owner.service bus-tracker-public.service
```

User services may stop after logout unless linger is enabled for the account. Keep the host awake for continuous public access.

The visitor path works whether Tailscale strips `/bus` before forwarding or preserves it; assets and API requests stay under `/bus/`. The owner dashboard remains at `http://127.0.0.1:8000/` and retains scheduled voice and local TTS controls.

## Run

Requires Python 3.10+ and internet access to the public Taipei and New Taipei bus feeds.

```sh
python -m bus_tracker.server
```

Open <http://127.0.0.1:8000>. The top of the page follows this order: route tabs with a **＋** add button, saved trips (with a compact empty state until one is saved), direction and stop, then **計算哪些來車？**. The latter states whether estimates include only this direction or another direction's possible next circuit. Its choice is saved per route and updates the vehicle list, departure advice, and periodic voice report; the official next-bus ETA stays independent. A next-circuit vehicle is counted only after its remaining leg, the turn between endpoints, and the selected leg's prefix; its ETA is conditional on the bus continuing service. A vehicle confirmed at a shared terminal can still be shown as already at that stop. Phone push and threshold alerts exclude conditional next-circuit arrivals. The arrival board puts the official next-bus ETA above every freshly detected approaching vehicle, numbered by estimated arrival order; it never hides following vehicles. Each bus row shows its next stop and estimated range, with position age, confidence, and calculation sources under expandable details. The official ETA is not tied to a particular license plate. On small screens the route panel displays one direction at a time and the map can be expanded; voice settings are collapsed beneath the enable and test buttons. The selected stop has a blue pointer and name on the map, separate from the orange and green direction lines. **常用行程** stores up to eight route, direction, stop, and opposite-direction presets in this browser. Selecting a stop immediately clears the previous stop’s ETA and buses, shows the new selection, then displays the newest cached snapshot while a fresh feed request completes. Deliberate selections and manual refreshes request fresh vehicle, event, and ETA data, with a shared five-second minimum refresh age to protect the upstream feed. The dashboard shows feed fetch age and each vehicle's last report age. Its low/medium/high confidence label is a heuristic based on vehicle age, route projection, observed travel, and recent arrival samples; it is not a probability. Routine polling remains every 30 seconds. The upstream feed may itself lag behind the bus. Run `python -m unittest discover -s bus_tracker -t . -p "test_*.py"` and `node bus_tracker/test_voice.js` for local tests.

The **使用目前位置** switch aligns with **步行到站** on desktop. It requests one browser location when enabled and again after a stop change. While active, **步行到站** shows the GPS estimate as a read-only value; turning it off restores the saved manual minutes. If geolocation is unavailable or denied, the switch returns to manual mode with a status message. The choice to use GPS lasts only for this page session. Coordinates stay in the browser; only the calculated walking minutes can be sent to the server for phone notifications. The technical report linked from the page explains the calculation and current UX limitations.

On phones, **更多路線** exposes offscreen tabs, the current route/direction/stop appears in a compact bar after scrolling past selection, and saved trips show the first three until expanded. GPS shows its acquisition time and has a **重新定位** button. Arrival rows separate buses approaching on this trip from those that might continue after a turn. The **建議出發時間** card contains the walking controls and, on the public phone page, **手機出發提醒**. Desktop hides the phone-only modes and notification button. **計畫模式** uses the recommendation already shown at the top of that card as the stop, walking time, or bus feed changes; the shared location switch obtains a one-time GPS estimate. The optional Web Push control stays available below both phone modes and can notify after the page closes. **前往站牌模式** continuously watches the phone location while the page is open, recalculates walking time on position updates, and compares it with fresh bus arrivals. It shows a prominent warning when the estimated walking time leaves less than two minutes of buffer or the next arrival looks unreachable. It does not measure actual walking speed or run reliably when the page is closed or suspended. It ignores stale positions, stale bus feeds, low-confidence vehicles, and speculative next-circuit arrivals. Returning to plan mode stops the continuous location watch. Phone push pins the chosen route, direction, and stop when enabled. Browsing other routes leaves that target intact; **改為提醒目前站牌** changes it explicitly. Walking-time changes resync only while viewing the pinned stop. A failed resync shows **重試同步**; until it succeeds, the phone may still track the previous stop. Updates carry increasing revisions so late old requests cannot override the latest stop or re-enable a removed subscription. The technical report explains the pinned target and what happens when its route tab is removed.

## Adding routes and where data lives

Press **＋** beside the route tabs to open **加入其他路線**, then search a name such as `0東`, or paste `https://pda5284.gov.taipei/MQS/route.jsp?rid=10841` from the official list. The browser calls `GET /api/catalog?q=...`. For a pasted link, `catalog.py` accepts only the official host and `/MQS/route.jsp` path, extracts the numeric `rid`, and looks it up in the Taipei and New Taipei Route feeds. A name search checks route names in those feeds and returns up to 25 matches. The app never downloads the pasted URL or scrapes its page to calculate arrivals. Select a result to load its official route metadata, stops, and live arrival data; a route absent from both feeds cannot be tracked. The initial three tabs remain available. Added tabs are capped at 20; selecting one shows a named remove button directly below the tabs.

The **route choice is per browser origin**, while live source data is shared by that server process:

| Location | Stored information | Example |
|---|---|---|
| Browser `localStorage` | Added route IDs (`bus-tracker-added-routes`), active route (`bus-tracker-route`), per-route direction, stop, and cross-direction choice (`bus-tracker-<route ID>-...`); saved trips (`bus-tracker-saved-trips`) | Adding 0東 saves `10841` in the added-route ID list. The browser does not save a copy of the full official stop list. |
| Server memory | Route metadata discovered from both official Route feeds, plus shared feed cache and recent stop-to-stop observations | On reload, `GET /api/routes?ids=10841` supplies the route name and directions; `GET /api/stops?route_id=10841` supplies its current stops. Route discovery checks the official feeds about hourly for new IDs; already loaded names stay in memory until restart. Vehicle, event, and ETA feeds use a 30-second cache. A restart clears these caches. |
| Server SQLite | Per-route prediction/arrival calibration files created when that route is tracked; phone push subscriptions when enabled | Opening 0東's arrivals creates `bus_tracker/arrival_history_10841.sqlite3`. Enabling a phone alert stores its selected route, stop, and subscription in `push_subscriptions.sqlite3`. |
| Owner-only server file | A daily speech schedule, only when the owner saves one | `bus_tracker/schedule.json` stores a scheduled route ID and stop; a public visitor adding a tab does not edit it. |

For example, adding 0東 on a phone does not add it on a PC. The public HTTPS page and either localhost port have different browser origins, so they also keep separate tab lists. Clearing that browser's site data removes its added tabs and saved trips; it does not delete the server's calibration history. Conversely, removing a tab changes that browser's list only, and does not stop someone else from using the same route.

## Data and accuracy

- Initial routes are 橘5 (`16405`), 908 (`16585`), and 921 (`16664`). Other Taipei and New Taipei routes are discovered from their official Route feeds. The New Taipei feed is [ntpcbus](https://tcgbusfs.blob.core.windows.net/ntpcbus/GetRoute.gz); the Taipei feed is [blobbus](https://tcgbusfs.blob.core.windows.net/blobbus/GetRoute.gz). Route IDs are looked up server-side; the pasted official webpage is never fetched as an arbitrary URL. A route absent from both feeds cannot yet be tracked, even if it appears on the official list (for example, an intercity service).
- `feeds.py` defines the compatible municipal feed sources, `catalog.py` validates searches and official route links, and `tracker.py` stores route metadata and calculates arrivals. `/api/catalog?q=...` searches up to 25 matching routes; `/api/routes?ids=...` loads saved route metadata. Feed payloads are shared across visitors while their added tabs stay in browser storage. Segment history and calibration databases are allocated only when a route is actually tracked.
- Stop order comes from the [Stop feed](https://tcgbusfs.blob.core.windows.net/ntpcbus/GetStop.gz). The next bus ETA comes from the [EstimateTime feed](https://tcgbusfs.blob.core.windows.net/ntpcbus/GetEstimateTime.gz). Individual locations come from the [BusData feed](https://tcgbusfs.blob.core.windows.net/ntpcbus/GetBusData.gz); terminal dwell state comes from the [BusEvent feed](https://tcgbusfs.blob.core.windows.net/ntpcbus/GetBusEvent.gz).
- 橘5 is a loop at 捷運景安站(景平路): the feed assigns that stop to return direction, though it follows outbound 中興街口. The app includes it at the end of outbound too. A bus that has switched to return direction is shown as “at this stop” on the outbound view only while a fresh stop event confirms it is stopped there. Following outbound vehicles remain visible behind it.
- 908 and 921 assign 景安站 to outbound travel. The app also includes it at the start of return travel and carries a stopped vehicle across directions only while a fresh stop event confirms it is there. Segment history and ETA calibration are separate per route. Long freeway gaps use a longer fallback when observed and official segment times are unavailable. Virtual nonboarding and temporarily removed stops appear on the route, but cannot be selected for tracking.
- The route panel shows each stop's official ETA/status and recent bus stop-event markers in both directions. The selected-stop list shows only buses still approaching that stop, with their next stop. It uses fresh stop events when GPS is unavailable, and uses GPS only when it agrees reasonably with the stop event. Data older than four minutes is ignored. Loops, overlapping streets, detours, poor GPS, or a bus about to start service can still give an incorrect order or omit a vehicle.
- The route sketch connects stop coordinates with straight lines; it is not a road-level route map.
- The official ETA feed reports one prediction per route and stop. It does not identify all following vehicles or give their individual ETAs. The official next ETA therefore remains separate from per-vehicle estimates.
- For each detected bus, the tracker adds the remaining stop-to-stop travel times between its mapped position and the selected stop. Each segment uses a recent observed passage of the same bus between adjacent stops when available; otherwise it uses a plausible positive difference between adjacent official stop ETAs, then falls back to a stop-distance estimate. Observed segment samples are held in server memory for up to three hours, so coverage improves while the dashboard is polled and resets when the server restarts. Each per-bus estimate has an uncertainty range; `arrival_history.sqlite3` stores recent forecasts and confirmed stop arrivals so the range can adapt to observed prediction errors. Before enough arrivals are observed, the range uses a conservative allowance based on the source of the segment times. This is an approximate range, not a statistical guarantee. Buses with no fresh position or stop event cannot be listed.
- The manual voice notifier uses the browser's `speechSynthesis` API or the selected local voice while this page is open. **到站提醒** announces the official ETA when it first enters the threshold and announces each tracked vehicle when its own estimate enters the threshold, with repeat suppression per vehicle. **定時播報** speaks the selected stop's live official status and estimated arrival time for every detected approaching bus immediately when enabled, then at the chosen interval (1–60 minutes). The enable button becomes available after live data loads; pressing it starts speech during the click so browsers that require a user gesture can play it. **試播目前資訊** provides a direct audio test, and the status line shows playback start, completion, or an error. If browser synthesis returns `synthesis-failed`, the local server renders a WAV via `libespeak-ng` and the page plays it as HTML audio. On Linux, install the `libespeak-ng1` and `espeak-ng-data` packages if this fallback is unavailable. Restart the server after updating the app. If the status says it is speaking but no sound is heard, check the browser tab's mute state and the system output device.

- **播報內容** defaults to 簡短: reports a numbered ETA for each tracked bus without license plates, next stops, or a duplicate official ETA. When no bus can be tracked, it reports the official status. 詳細 preserves the longer report with the official ETA, plates, next stops, and distance details. Both Chinese and English reports group next-circuit vehicles after one warning that they must continue service beyond the terminal. The browser saves this choice; saving the owner's daily schedule includes it. Existing saved cron schedules stay on their previous detailed wording until resaved.

## Departure advice and daily voice schedule

The **使用目前位置** switch asks the browser for one location fix. Coordinates stay in the browser. It estimates walking time from straight-line distance, a 35% detour factor, location accuracy, and a 1.2 m/s walking pace; this is not a walking route. Changing stops clears that estimate. The manual walking time remains available. The public HTTPS page offers **手機出發提醒**, which subscribes this device to Web Push for the currently selected stop and walking time. The chosen stop stays pinned while browsing; a change of walking time updates the subscription when the pinned stop is on screen. The server checks every 30 seconds and sends a notification when a fresh official ETA or eligible vehicle estimate enters the walking time plus two-minute leave window. Notifications can arrive after the page closes, subject to browser and phone delivery. On iPhone/iPad, add the public page to the Home Screen before enabling notifications. This feature requires Python `cryptography` and `requests`; the public server stores its VAPID private key in `bus_tracker/push_vapid.pem` and subscriptions in `bus_tracker/push_subscriptions.sqlite3`. Keep the private key private and persistent; changing it requires devices to subscribe again. Push alerts are visual notifications, not background voice playback. The owner's daily cron voice schedule is separate.

Set **步行到站** to your estimated walking time, or use the current-location button for a rough estimate. The recommendation allows that time plus a fixed two-minute buffer. If the official next ETA is too soon, it looks for the earliest direct vehicle whose lower ETA bound still leaves enough time, then a next-circuit vehicle if no direct one qualifies. Next-circuit advice says the vehicle must continue service at the endpoint. The page updates advice and displayed per-vehicle ETA ranges every ten seconds between feed polls, aging official ETA from the feed fetch time and vehicle estimates from their report times. **到站提醒** offers 1, 3, 5, and 10-minute presets or a custom whole-minute threshold from 1 to 60; the selected value also works in the owner's saved cron schedule.

The **朗讀語音** menu offers the local OpenAI-compatible TTS server at `http://localhost:8001/v1/audio/speech`, eight eSpeak variants for the selected language, and matching voices installed in the browser. The local TTS fields default to `model=tts-1` and `voice=anne`, and request WAV audio as in the example API call. This server does not expose a voice catalog, so enter the model and voice names supported by your server. The dashboard proxies and normalizes its WAV response before playing it. The choice and API fields are saved in this browser. Browser synthesis failures fall back to standard eSpeak. Click **試播目前資訊** after selecting a voice.

Set **播報語言** to 中文 or English. This changes the spoken alert, periodic briefing, test message, browser voice choices, and saved cron report; the dashboard labels remain Chinese. English reports use the official `nameEn` value from the public stop feed and expand common abbreviations for speech. English mode also offers eight English eSpeak variants and falls back to English eSpeak if browser synthesis fails. Language and voice choices are saved in this browser. Save the cron schedule again after changing the language or voice so its stored settings match the page.

Choose a route tab, stop, voice mode, and **每天定時啟動**; set a local start time and duration (1–720 minutes), then click **儲存排程**. This installs one named entry in your user crontab while retaining other entries, and saves the route, stop, mode, interval or threshold, language, and local voice in `bus_tracker/schedule.json`. At that time each day, cron starts a polling process that continues for the configured duration. Briefing mode speaks immediately and at the selected interval; alert mode speaks an initial report, then reports each newly approaching vehicle and the official threshold crossing. The process stops early if the saved schedule changes or is disabled, and a lock prevents overlapping runs. It works without the dashboard tab or server running, provided the computer is awake, cron is active, an audio session is available, and the bus feed is reachable. The local TTS server must also be running if selected. Browser voices use standard eSpeak in cron because browser voices cannot run there. To disable the job, uncheck **每天定時啟動** and save. On Linux this feature needs `cron`, `pulseaudio-utils`, and `libespeak-ng1` installed.

## Optional spoken queries with speech-to-speech

The included `bus_tracker.voice_tools` module exposes a read-only live-arrival tool to [Hugging Face speech-to-speech](https://github.com/huggingface/speech-to-speech). In a separate Python 3.11+ environment, install that package and run from this repository's parent directory:

```sh
speech-to-speech local --tool-module bus_tracker.voice_tools --stt paraformer \
  --init_chat_prompt "You are a Traditional Chinese bus assistant. For current Taipei or New Taipei arrivals, call get_bus_arrivals. Ask for the official route ID, stop and direction if missing. Distinguish the official next ETA from each detected bus's estimated arrival time, and label the latter as an estimate."
```

The models download on first run. The package's default speech recognizer covers European languages, so a Chinese-capable STT backend such as Paraformer or Whisper is needed. The tool module itself is tested for Python syntax, but the voice pipeline has not been installed or run here. Web Push leave alerts are configured separately on the public dashboard.
